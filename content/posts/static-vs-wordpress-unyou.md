構築を始める前、WordPressと静的サイト(Hugo)を比較する記事を書きましたが、あくまで「調べた内容」でした。実際に数週間運用してみて、当時の予想と実感が一致した部分・違った部分があったので振り返ります。

## 事前に予想していたこと

| 項目 | 事前の予想 |
|---|---|
| セキュリティ | 静的サイトの方が攻撃対象面が小さく安全 |
| 速度 | 静的サイトの方がDBを介さない分、表示が速い |
| 更新の手間 | WordPressの方が管理画面から直接編集できて楽 |

## 実際に運用してみて

### セキュリティ面は予想通り、負担がかなり軽かった

WordPressであれば必要になる、プラグインの脆弱性対応や、ログイン画面への攻撃対策といった作業が一切不要でした。実際に発生したトラブルは、`baseURL`の設定ミスや文字コード、ファイル権限といった**自分の操作ミスによるもの**がほとんどで、外部からの攻撃を意識する場面はほぼありませんでした。これは想定通りの利点でした。

### 更新の手間は「思ったより平坦ではなかった」

事前の想定では「WordPressの方が楽」という程度の認識でしたが、実際にはHugoでの更新作業自体は

```
記事を書く → hugo → scp → chmod → 確認
```

という決まった手順さえ覚えてしまえば、数分で完結する作業でした。ただし、**この「手順を覚えるまで」のコストは、事前の想定より高かった**というのが実感です。WordPressであれば管理画面からボタン操作で完結する作業が、静的サイトでは複数のコマンドの意味を理解して初めて安定して行えるようになる、という違いがありました。

### 想定していなかった手間:デプロイのたびの権限トラブル

これは事前に全く想定していなかった点です。ファイルを転送するたびに権限が引っかかる、という現象は、WordPressであれば意識する必要のない領域でした。静的サイトだからこそ意識することになった、良くも悪くも「学びの多い」ポイントでした。

## 総合的な感想

| 観点 | 感想 |
|---|---|
| セキュリティ・軽さ | 静的サイトの利点をそのまま実感できた |
| 学習効果 | 想定以上に高かった。DNS、SSH、ファイル権限まで一通り触れることになった |
| 導入のハードル | 事前の想定より高かった。ただしこれは「学習目的」であれば長所でもある |
| 純粋な運用の楽さ | WordPressの方が上、という事前の想定は変わらず |

「収益を早く出したい・とにかく楽に更新したい」という目的であれば、今でもWordPressの方が適していると思います。ただ、今回のように「インフラを学びながら発信する」という目的であれば、事前に想定していた以上に、静的サイト構成は学びの機会を提供してくれたと感じています。
