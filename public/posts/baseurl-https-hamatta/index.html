hugo.tomlの文字化け事件と、HTTPS化(Let's Encrypt)でハマった話

2026.09.05

Google Search Consoleにサイトマップを登録しようとしたところから始まった、想像以上に長いトラブルシューティングの記録です。文字化けとHTTPS化、2つの問題が絡み合っていました。

発端:サイトマップが「無効」と言われる

Search Consoleでサイトマップ(sitemap.xml)を送信したところ、

サイトマップ アドレスが無効です

と表示されました。実際にブラウザでsitemap.xmlを開いてみると、中のURLがすべて

https://example.com/posts/...

という、ダミーのドメインのままになっていました。原因はhugo.tomlのbaseURLが、サイトを最初に作った際の仮の値のまま残っていたことでした。

文字化け事件のはじまり

baseURLを実際のドメインに書き換えようと、メモ帳でhugo.tomlを開いて1行だけ修正して保存したところ、ファイル全体の日本語がすべて文字化けするという事態になりました。

description = "螟ｧ蟄ｦ縺ｧHTML/CSS繧貞ｭｦ繧薙□遲・・′..."

原因の切り分け

これが単純そうに見えて、実は2段階の問題が絡んでいました。

1段階目:文字コードの不一致

メモ帳で保存する際の文字コードが、元のファイル(UTF-8)と噛み合っていなかったことが原因でした。typeコマンド(PowerShell)で中身を見ると化けて表示されましたが、これは実は表示コマンド側の癖で、必ずしもファイル自体が壊れているとは限らない、という点も分かりにくいポイントでした。

Get-Content -Path hugo.toml -Encoding UTF8

このコマンドで見ると正しく表示されることがあり、typeだけで「文字化けした」と判断するのは早計だと学びました。

2段階目:BOM付きUTF-8の罠

一度はGet-Contentで正常に見えたものの、hugoコマンドを実行すると今度は別のエラーが出ました。

unmarshal failed: toml: invalid character at start of key: U+00EF 'ï'

これは、メモ帳が「UTF-8」として保存する際、ファイルの先頭に目に見えない**BOM(Byte Order Mark)**という印を付けてしまうことが原因でした。Hugoはこの印を不正な文字として扱ってしまいます。

解決:PowerShellで直接、BOM無しのUTF-8として書き出す

メモ帳を経由するとまた同じ問題が起きる可能性があったため、PowerShellのコマンドで直接ファイルを生成する方法に切り替えました。

$text = @"
(ファイルの中身をここに)
"@
[System.IO.File]::WriteAllText("$PWD\hugo.toml", $text, (New-Object System.Text.UTF8Encoding $false))

UTF8Encoding $falseの部分が「BOMを付けない」という指定です。これで文字化けは解消しました。

⚠️ 教訓:日本語を含む設定ファイルをWindowsのメモ帳で編集するのは、文字コードの罠(Shift-JISとの混同、BOM付与)が多く、事故が起きやすい。PowerShellから直接ファイルを生成する方法の方が、結果的に確実だった。

次の壁:サイトマップがまだ無効

baseURLを直してビルド・転送し直しても、まだSearch Consoleでは

取得できませんでした

と表示され続けました。今度はブラウザで直接https://でアクセスを試したところ、

接続できません

というエラーになりました。サイトがまだHTTP(暗号化なし)でしか公開されておらず、baseURLはHTTPSを前提にしていたという、ちぐはぐな状態になっていたのが原因でした。

HTTPS化(Let’s Encrypt)を実施

このタイミングで、以前後回しにしていたSSL化に着手しました。

sudo apt install certbot python3-certbot-nginx -y
sudo certbot --nginx -d (ドメイン) -d www.(ドメイン)

メールアドレスの入力、利用規約への同意を経て、証明書の取得とNginxの設定変更が自動で行われました。

https://(ドメイン)

で、鍵マーク付きの安全な接続が確認できました。

転送のたびに再発した403エラー

HTTPS化の作業とは別に、ファイルをscpで転送し直すたびに、以前解決したはずの**403 Forbidden(権限エラー)**が再発しました。原因は毎回同じで、転送されたファイルの権限がNginxから読み取れない状態になっていたためです。

sudo chmod -R 755 /var/www/yourlog

これを転送後の定型作業として組み込むようにしました。

最終的にサイトマップは成功

すべて解決した後、Search Consoleでサイトマップを再送信したところ、

✓ サイトマップは正常に処理されました
検出されたページ数: 23

と表示され、無事に完了しました。

つまずきポイントのまとめ

つまずいたこと 原因 学んだこと
サイトマップが無効と言われた baseURLが仮のドメイン(example.com)のままだった 設定ファイルの初期値を見落とさない
hugo.tomlが文字化けした メモ帳の文字コード設定(BOM付きUTF-8)がHugoと相性が悪かった 日本語ファイルの編集はPowerShellで直接書き出す方が確実
HTTPSでサイトマップにアクセスできなかった サイトがまだHTTP対応のみで、HTTPS化が済んでいなかった baseURLをhttps://にする前提として、SSL証明書の導入が必要
転送のたびに403エラーが再発した scpで転送するたびにファイル権限がリセットされていた 転送後はchmodをセットの作業として習慣化する

1つのエラーの裏にもう1つ別の原因が隠れている、という展開が多く、原因を1つ直したら解決したと思ったら次のエラーが出る、を何度か繰り返しました。地道な切り分けの繰り返しでしたが、最終的にSearch Consoleで成功表示が出たときは、これまでで一番達成感がありました。
