文字コード沼:UTF-8・BOM・Shift-JISは何が違うのか

2026.09.06

hugo.tomlの文字化け事件をきっかけに、「文字コード」というものをちゃんと理解しないまま今まで来ていたことに気づいたので、改めて整理してみます。

そもそも文字コードとは

コンピュータは文字を直接理解できず、すべての文字を数字に変換して扱っています。 「あ」という文字を、どの数字に対応させるかというルール(対応表)が「文字コード」です。この対応表が送り手と受け手でズレると、文字化けが起きます。

主な文字コードの違い

文字コード 特徴
Shift-JIS 古くからある日本語Windows標準。1バイトまたは2バイトで1文字を表す
UTF-8 世界中の文字を1つの体系で扱える、現在の標準。可変長(1〜4バイト)で表現
UTF-8 (BOM付き) UTF-8の先頭に、「これはUTF-8です」という目印(BOM)を付けたもの

今回起きたことの正体

1段階目:Shift-JISとUTF-8の混同

メモ帳で保存する際、元のファイル(UTF-8)とは違う文字コード(Shift-JISに近いもの)で保存されてしまい、日本語の部分が化けました。

description = "螟ｧ蟄ｦ縺ｧHTML/CSS..."

これは「UTF-8のバイト列を、Shift-JISのルールで無理やり読んでしまった」ときに出る、典型的な化け方です。

2段階目:BOM付きUTF-8とHugoの相性

文字コードをUTF-8に合わせ直した後も、今度は別のエラーが出ました。

unmarshal failed: toml: invalid character at start of key: U+00EF 'ï'

これは、メモ帳が保存する「UTF-8」が、実際には先頭にBOMという目印付きだったことが原因でした。BOM自体は正当な仕組みですが、TOML形式(hugo.tomlが使っている設定ファイルの書式)の仕様上、このBOMを不正な文字として扱ってしまうという、相性の問題でした。

なぜtypeコマンドでは化けて見えたのか

さらにややこしかったのが、PowerShellのtypeコマンドが、正しく保存されたUTF-8ファイルであっても、古い文字コード前提で表示しようとする癖があることでした。

type hugo.toml        # 化けて見える
Get-Content hugo.toml -Encoding UTF8   # 正しく見える

同じファイルなのに、見るためのコマンドによって結果が変わる、というのは最初かなり混乱しました。

得られた教訓

  • 文字化けを見たとき、「ファイルが壊れている」のか「見る側のコマンドが対応していないだけ」なのかを区別する
  • 日本語を含む設定ファイルは、GUIのメモ帳よりも、文字コードを明示的に指定できるコマンド(PowerShellなど)で編集する方が事故が少ない
  • 「UTF-8」と一言で言っても、BOMの有無で挙動が変わる場合があるということを知っておく

普段何気なく保存している文字が、裏側でこんなに複雑なルールに支えられていると実感した出来事でした。
