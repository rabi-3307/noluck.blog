記事を書いてから公開するまでの手順(PowerShellでの操作の流れ)

2026.09.05

記事を書くたびに「あれ、この後何のコマンドを打つんだっけ」となることが多かったので、書き始めてから実際に公開されるまでの一連の流れを、手順としてまとめておきます。特に転送のたびに毎回再発した403エラーは、何度もハマったのでしっかり書き残しておきます。

全体の流れ

1. 記事を書く(ローカルのcontent/posts/)
2. プレビューで確認する(hugo server)
3. 本番用にビルドする(hugo)
4. サーバーに転送する(scp)
5. 権限を直す(chmod)  ← 実は毎回必須だった
6. Nginxを再起動する

当初は「5番は初回だけ直せば済むはず」と思っていたのですが、実際には転送のたびに再発することが分かったので、今は「毎回必ずやる手順」として組み込んでいます。1つずつ見ていきます。

ステップ1:記事を書く

PowerShellで、プロジェクトのフォルダに移動します。

cd "C:\Users\user\...\yourlog-site"

新しい記事ファイルを作成します。

hugo new posts/kiji-no-namae.md

生成されたcontent/posts/kiji-no-namae.mdをVSCodeなどで開き、本文を書いていきます。

ステップ2:プレビューで確認する

書きながら、随時見た目を確認します。

hugo server

Web Server is available at http://localhost:1313/

ブラウザでhttp://localhost:1313を開いて確認します。保存するたびに自動で反映されるので、書いては確認、を繰り返します。

確認が終わったら、ターミナルに戻って停止します。

Ctrl + C

ステップ3:本番用にビルドする

記事が書き終わったら、公開用のファイル一式を生成します。

hugo

これでpublicフォルダの中身が最新の状態に更新されます。

ステップ4:サーバーに転送する

scpコマンドで、VPS上の公開フォルダに転送します。

scp -r public\* root@(サーバーのIPアドレス):/var/www/yourlog/public/

パスワードを聞かれず転送が始まれば、公開鍵認証が正しく機能している証拠です。

ステップ5:権限を直す(ここが今回一番の学び)

転送直後、ブラウザで確認すると**「403 Forbidden」**と表示されることが、これまで複数回発生しました。最初は「初回だけの一時的な不具合」だと思っていたのですが、記事を追加してscpで再転送するたびに、同じ症状が繰り返し起きることが分かりました。

原因は毎回同じで、scpで転送されたファイル・フォルダの権限が、Webサーバー(Nginx)から読み取れない状態にリセットされてしまうためです。

SSHで接続します。

ssh root@(サーバーのIPアドレス)

権限を直します。

sudo chmod -R 755 /var/www/yourlog
sudo chmod 755 /var/www

ステップ6:Nginxを再起動する

sudo systemctl restart nginx

確認

すべて終わったら、実際の公開URLで最終確認します。

https://(あなたのドメイン)

Ctrl + Shift + R(強制リロード)も忘れずに試すと確実です。特にCSSファイル単体で確認すると分かりやすいです。

https://(あなたのドメイン)/css/style.css

ここが403 Forbiddenになっていたら、権限の問題がまだ残っている合図です。CSSの中身(コード)がそのまま表示されれば、正しく直っています。

つまずいたポイント

つまずいたこと 原因 学んだこと
hugo serverで確認した後、公開してもサイトが変わらない hugo serverは本番用のファイルを更新するコマンドではなかった 公開前は必ずhugo(サーバー無し)を実行する習慣をつける
scp転送のたびに403エラーが再発する scpは転送するたびにファイルの権限をリセットしてしまう 「初回だけ直せばいい」ものではなく、転送のたびに必ずchmodする、と手順そのものに組み込む
毎回cdを打つのを忘れる ターミナルはPowerShellを開き直すたびに現在地がリセットされる フォルダをエクスプローラーで開いてからターミナルを起動すると手間が減る

今の「型」として定着させた手順

結局、記事を更新するたびに以下をワンセットで実行する、というのが今の運用の型になりました。

# 1. ビルド
hugo

# 2. 転送
scp -r public\* root@(IPアドレス):/var/www/yourlog/public/

# 3. SSHで権限修正 + 再起動(毎回セットで)
sudo chmod -R 755 /var/www/yourlog
sudo systemctl restart nginx

「書く→確認→ビルド→転送→権限修正→再起動」の6ステップを毎回同じ順番で繰り返す、と割り切ってしまえば、実はそこまで複雑な作業ではありませんでした。むしろ、この権限の再発パターンに気づけたこと自体が、地味ながら実用的な学びだったと思います。
